    7. Data Architecture¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    7.1 FITS file structure as lightkurve/astropy deliver it¶

    Raw photometry arrives as FITS files fetched by lightkurve.search_lightcurve(...).download_all(...). This codebase does not parse FITS structure directly — no astropy.io.fits calls appear anywhere in src/exocomet/; all FITS handling is delegated to lightkurve, which returns a LightCurveCollection that this project immediately .stitch()es into one combined lightkurve.LightCurve object before ever touching its own types. io/download.py's module docstring states this design choice directly: "Only this module knows about lightkurve... everything downstream operates on LightCurveData... so the science code neither knows nor cares where the photometry came from." Consequently, this document does not attempt to describe Kepler/TESS FITS extension layout (e.g. LIGHTCURVE/APERTURE HDUs) — that structure is entirely internal to lightkurve and never surfaces past _to_light_curve_data (io/download.py).

    7.2 The fields this codebase actually reads¶

    _to_light_curve_data (io/download.py) pulls exactly three arrays off the stitched lightkurve object — lc.time.value, lc.flux.value, lc.flux_err.value — and constructs LightCurveData (core/types.py) from them:

    LightCurveData field Type Meaning
    target_id str Catalogue identifier, e.g. "KIC 3542116"
    mission str "Kepler", "K2", or "TESS"
    time float64 array Days; BKJD for Kepler, BTJD for TESS
    flux float64 array Normalised so out-of-transit ≈ 1.0
    flux_err float64 array Per-cadence uncertainty, same normalised units as flux
    meta dict[str, Any] Free-form provenance (see below)

    Quality flags are not retained as a separate array. lightkurve's download_all(..., quality_bitmask=quality_bitmask) call applies a quality mask during the download step (default "default", meaning cadences the mission pipeline flagged as bad are already removed before lightkurve hands back the light curve) — but the underlying per-cadence quality bitmask itself is never carried into LightCurveData. Downstream code cannot ask "was this specific cadence flagged, and for what reason" — only "was it already excluded by the mask applied at download time." This is a real, load-bearing gap: any candidate event should be understood as having survived whatever quality_bitmask="default" excludes, and nothing more granular is currently recorded or queryable. NOT IMPLEMENTED as a first-class field.

    meta does carry real provenance, populated at two points: - _to_light_curve_data: n_dropped_nonfinite, n_dropped_duplicate_timestamp, median_raw_flux, source="MAST". - fetch_light_curve's extra_meta: n_products, author, exptime (None for non-TESS), sectors_or_quarters (best-effort extracted list of sector/quarter numbers actually used).

    Cadences with non-finite time, flux, or flux_err are dropped outright (good = np.isfinite(time) & np.isfinite(flux) & np.isfinite(flux_err)), and duplicate timestamps (from overlapping quarters/sectors) are also dropped, with the count logged rather than silently discarded — the module docstring notes this is deliberate: "a large count here is itself a sign that mismatched products... got stitched together."

    7.3 Temporary-data lifecycle: download → extract → delete¶

    The canonical ordering is implemented in scripts/ingest.py's process_one_target, and its module docstring is explicit that the order is the safety mechanism, not a transaction:

    1. Fetch the light curve from MAST — raw FITS lands on local disk (data/raw/ by default), not yet deleted.
    2. Save the extract to disk, atomically (io/extract.save_extract, see 08_storage.md).
    3. Only now, delete the raw FITS (shutil.rmtree(raw_cache_dir / "mastDownload", ...)).
    4. Run the detection pipeline (detrend + detector) on the extract.
    5. Write the results file, atomically.
    6. Only now, append one ledger line recording success.

    If the process is killed anywhere before step 6, no ledger entry exists for that attempt, so the target is simply retried on the next run — steps 2 and 5 are each independently atomic (os.replace-based), so a killed run never leaves a half-written extract or results file, only, at worst, a missing one. This ordering is deliberately conservative about when raw FITS is deleted: discard_after_read=False is passed to fetch_light_curve inside process_one_target specifically so the FITS survives until after step 2 lands durably — the module docstring notes that deleting it as a side effect of fetch_light_curve itself (as discard_after_read=True does elsewhere) "would collapse steps 1 and 3 into one, removing the ordering guarantee this function exists to provide."

    A real, previously-shipped bug in this exact lifecycle (Findings Log, 2026-09-14): discard_after_read=True's cleanup step (_discard_cached, io/download.py) originally matched a normalised slug of the catalogue target_id (e.g. "kic1161345") against downloaded cache directory names to decide what to delete. lightkurve names its cache directories after its own pipeline-internal identifiers, never the search string used — a Kepler product is kplr001161345_lc_... (no "kic" substring anywhere), and a TESS HLSP product embeds a zero-padded TIC number mid-filename, unrelated to a resolved common name like "beta Pic" (itself containing no digits at all). The slug never matched anything, for any target, on either mission — this had presumably been true since the function was first written, and was found only when data/raw/ was observed to have grown to 166 MB despite every download supposedly discarding after read. Fixed: _discard_cached now wipes the entire mastDownload tree under the cache directory rather than attempting to match subdirectories by name — correct as long as targets are processed one at a time, which is true of every current caller, but explicitly noted (in the function's own docstring) as needing per-target cache subdirectories once a parallel-worker batch (Next Steps E4) is built.

    7.4 Data retention policy¶

    Data Retained? Where
    Raw FITS No — deleted after extraction (§7.3) or immediately via discard_after_read=True in ad-hoc use data/raw/mastDownload/ (transient only)
    Extract (time/flux/flux_err + metadata) Yes — the permanent, detector-independent record of what was measured <data-repo-dir>/extract/<mission>/<target>.parquet (see 08_storage.md)
    Results (candidate events, one pipeline version's output) Yes <data-repo-dir>/results/<mission>/<target>.jsonl
    Processing ledger (append-only attempt log) Yes, indefinitely, append-only <data-repo-dir>/ledger.jsonl

    This is a deliberate design decision, not an oversight: the archive (MAST) is public and permanent, so mirroring it locally is storage spent on something already guaranteed to exist (io/download.py module docstring). The Findings Log (2026-09-13) records the actual scale reasoning behind this: one Kepler star's full extract is ~7.7 MB and takes ~62 s to download (latency-dominated across ~18 separate files); a full Kepler-scale mirror (200k stars) would be roughly 1.5 TB and 1–3 weeks of downloading on the author's own connection, against only 24 GB of free local disk at the time — download, not compute, is the binding constraint, and it is a constraint the stream-and-discard architecture sidesteps entirely by never needing to hold more than one star's raw data at a time.
