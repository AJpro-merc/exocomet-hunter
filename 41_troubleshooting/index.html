    41. Troubleshooting¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051. Every incident below actually happened during development, sourced from Session Log 2026-09-15.md. These are recorded so the same root cause doesn't need rediscovering.

    41.1 MAST fetch appears to hang for minutes with zero progress¶

    What you'll see: a call into io/download.py's fetch path (directly, via exocomet run, or inside scripts/ingest.py/train_classifier.py) sits with no CPU activity for several minutes.

    What it actually is: a truncated, previously-cached FITS file from an interrupted prior download — the real 2026-09-14 incident was a file sitting at exactly 65,536 bytes (a round 64 KiB block boundary), the signature of a killed mid-transfer download, silently left in the local cache. Retrying against it without clearing it first fails identically, every time, for as long as retries continue — not a true hang, just an unbounded number of guaranteed-identical failures with no time limit.

    Fix, already applied: io/download.py has bounded timeout + retry with explicit astroquery.mast.conf.timeout/pagesize configuration, and _call_with_retries now accepts a cleanup callback wired to _discard_cached(cache, target_id) between attempts — a poisoned cache entry is discarded before the next attempt, not retried against unchanged. If this recurs: check the cache directory for a file at a suspiciously round byte size (a multiple of 4096 or 65536 is a strong signal), quarantine or delete it, and confirm the error message names "may be corrupt due to an interrupted download" — that specific astroquery/lightkurve error string is the diagnostic signature, not a generic timeout.

    41.2 A ledger line says "success" but the output file doesn't exist¶

    Root cause, already fixed: this was the direct downstream consequence of §41.1's poisoned-cache pattern colliding with a retry loop that had no cleanup step — a run could log success from a stale code path before the underlying corrupted-cache failure was actually resolved. Fixed by the same cleanup callback above, plus an added immediate readback check in scripts/ingest.py right after save_extract(), specifically so this exact failure mode cannot recur silently from some other, future cause either. If you see it recur: check whether the readback check itself was bypassed (e.g. a code path that calls the underlying save function directly, skipping ingest.py's wrapper).

    41.3 ingest.py (or a sibling script) creates its cache in the wrong place¶

    What you'll see: a data/raw/ directory appears somewhere unexpected — e.g. under scripts/ — instead of at the repository root where every other tool expects it.

    Root cause: DEFAULT_CACHE_DIR = Path("data/raw") in the download module is relative to the process's current working directory, not the repository root. Running a script from inside scripts/ (a convention several sibling scripts use) silently creates scripts/data/raw/.

    Fix, already applied in ingest.py: it computes an explicit raw_cache_dir from Path(__file__).resolve(), independent of CWD, and passes it explicitly into fetch_light_curve. If you write a new script that touches the cache: do the same — never rely on fetch_light_curve's CWD-relative default from a script that might be invoked from an unpredictable working directory (e.g. CI, or a different shell session).

    41.4 git push fails with "Device not configured" or an account-mismatch error¶

    Root cause: the local machine's active gh credential is for a different GitHub account (elpis-app) than the one these two repositories (exocomet-hunter, exocomet-hunter-data) live under (AJpro-merc). A plain git push silently tries to authenticate as the wrong account.

    Workaround (in active use, including by the CI workflows themselves):

    GH_TOKEN=$(gh auth token -u AJpro-merc)
git push https://AJpro-merc:${GH_TOKEN}@github.com/AJpro-merc/exocomet-hunter.git

    Status: workaround only. A persistent local credential-config fix (so this doesn't need rediscovering each session) is explicitly listed in Next Steps.md's "FIRST THING NEXT SESSION" list as still outstanding — do not assume it has been permanently fixed just because the workaround exists.

    41.5 GitHub Actions silently burns compute and produces nothing¶

    What happened, real incident, 2026-09-14→15: train.yml failed 4 consecutive times, each run taking roughly 30–38 minutes, for a total of ~2 hours 16 minutes of real compute with zero output.

    Root cause: a 2026-09-14 force-push (squashing commit history to remove stray attribution) orphaned the branch reference the scheduled trigger was checking out — the runner's installed package version string showed it was still checking out the pre-squash commit, not current main. This is a real, non-obvious failure mode of combining scheduled workflow triggers with history-rewriting pushes: the schedule kept firing against a commit that no longer existed on the branch it thought it was tracking.

    Also found in the same investigation: a genuine architectural misunderstanding was corrected mid-session — the 2-hourly schedule only generates training rows (fetch → extract features → discard FITS → save), while actual model training is a separate weekly job (0 6 * * 1 in train.yml) that had never actually run; all 4 failures were generation runs, not training runs.

    Fix: both survey.yml and train.yml were disabled (gh workflow disable) pending a real commit to re-anchor main past the orphaned reference. A subsequent real commit (afa4bb2) did re-anchor the branch. If a scheduled workflow starts failing immediately after a force-push or history rewrite, check this first — it is a specific, previously-confirmed cause, not a generic "something broke" symptom.

    41.6 Quick diagnostic checklist¶

    Symptom Check first
    Fetch hangs / times out Cache directory for a truncated file at a round byte size
    Ledger says success, file missing Whether the save path went through ingest.py's wrapper (readback check) or bypassed it
    Wrong cache directory appears What CWD the script was invoked from, and whether it computes its cache path from __file__
    git push fails with auth error Active gh account (gh auth status) versus the repo's actual owner
    Scheduled Action fails immediately after a force-push Whether the branch reference the trigger checks out still exists
