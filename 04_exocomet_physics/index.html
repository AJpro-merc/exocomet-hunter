    4. Exocomet Physics¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    4.1 Nucleus, coma, dust tail, gas tail¶

    A comet is a small (kilometre-scale), volatile-rich body. As it approaches its star, solar/stellar heating sublimates surface ices, releasing gas and entrained dust that form a coma around the nucleus and are swept by radiation pressure and stellar wind into a trailing tail — generally a dust tail (curved, following the orbital path) and, closer in, a gas/ion tail (more nearly radially aligned with the star). None of this physical structure is separately modelled in this codebase — no nucleus/coma/tail geometry, optical depth, or orbital-dynamics simulation exists in src/exocomet/ as of this commit. NOT IMPLEMENTED. What is implemented is a photometric consequence of this structure: an asymmetric, extended obscuration profile, described below and modelled directly as a parametric light-curve shape rather than derived from a physical dust-tail simulation.

    A physically-grounded forward model (nucleus/tail geometry, optical depth, orbital velocity, limb darkening → simulated light curve) is explicitly PLANNED, not built: Next Steps item F2 and its sharper restatement J5 both describe this as the single highest-leverage improvement to the project's training data, precisely because the current injected/fitted shapes (described below) are a piecewise-empirical stand-in for it, not a physical simulation.

    4.2 Transit geometry: impact parameter and duration¶

    The general transit-geometry concepts — impact parameter (how centrally the transiting body crosses the stellar disc) and transit duration (set by orbital velocity, stellar radius, and impact parameter) — apply to an exocomet transit as they do to any transit, but this codebase does not model them explicitly as physical parameters. DipEvent.window (core/types.py, an EventWindow) records only the empirical start/end index and time of a detected dip, and event duration is read directly off the light curve (EventWindow.duration_days), not derived from an orbital/geometric model. Impact parameter is not represented anywhere in the codebase. NOT IMPLEMENTED as a physical quantity; what exists is the empirical geometric measurement only.

    4.3 Dust-tail geometry and optical depth: the model actually implemented¶

    The photometric model this project fits — and the one all of section 5's discussion of shape statistics is built on — lives in src/exocomet/detect/model_comparison.py. Its module docstring states the physical motivation directly:

    "Comet — a Gaussian ingress joined at the minimum to an exponential egress. This is the standard optically-thin dust-tail parameterisation: the obscuration builds as the head approaches and then decays as the tail sweeps out."

    This is an optically-thin approximation: the model does not represent a spatially resolved dust column with its own optical-depth profile; it represents the net fractional flux loss over time as a two-piece analytic curve. Concretely (comet_profile, model_comparison.py):

    • Ingress (falling side, t ≤ t0): flux = baseline − depth · exp(−½((t − t0)/σ)²) — a Gaussian, parameterised by ingress_width (σ, in days). This represents the compact, relatively opaque head/nucleus region blocking light as it approaches conjunction.
    • Egress (rising side, t > t0): flux = baseline − depth · exp(−(t − t0)/τ) — an exponential decay, parameterised by egress_tau (τ, in days). This represents the more extended, progressively less opaque trailing dust tail clearing the line of sight.

    The two halves are joined continuously at the minimum t0, both reaching baseline − depth there (comet_profile docstring: "The two halves meet continuously at the minimum, both reaching baseline - depth there"). depth is the fractional flux loss at minimum; baseline is the local out-of-dip flux level. A lower bound of 1.0e-4 days (_MIN_WIDTH_DAYS) is applied to both σ and τ during fitting, purely to prevent the optimiser from collapsing either width onto a single cadence — this is a numerical safeguard, not a physical claim about minimum tail width.

    For contrast, the competing symmetric model (symmetric_profile) is a single Gaussian with one shared width parameter on both sides — the shape expected from a solid, opaque, disc-shaped occulter (a planet) or from ordinary noise/artefact excursions. Section 5 covers how the two are compared.

    4.4 The photometric signature: depth, symmetry, and long egress¶

    The observable signature can be framed this way, consistent with the code above:

    • Flux reduction / depth. For the primary validation target, KIC 3542116, published depths span 491–1900 ppm (0.05%–0.19% of the star's brightness); per-measurement noise in that star after detrending is ~83 ppm, so even the deepest published event is only ~23× the noise of a single measurement (Findings Log, 2026-09-13).
    • Symmetry vs. asymmetry. A planet's transit is symmetric because the same opaque, fixed-size disc covers and uncovers the star at the same rate. An exocomet's transit is asymmetric because the head (compact, more opaque) and the tail (extended, less opaque, still clearing after the head has passed) are physically different structures with different obscuration timescales — the fast-fade/slow-recovery pattern the comet_profile Gaussian-ingress/exponential-egress shape is built to capture.
    • Long egress as the diagnostic feature. The physically meaningful statement, in this project's own terms, is τ/σ > 1: an egress timescale (τ) longer than the ingress width (σ) indicates a trailing tail — obscuration that clears more slowly than it accumulated. ModelComparison.tau_over_sigma (core/types.py) is the code's direct implementation of this ratio. Section 5 (05_detection_theory.md) covers why this fitted-profile ratio, rather than a simpler duration comparison at a fixed depth level, is the statistic this project actually uses to decide whether an event is comet-shaped.

    4.5 What is explicitly not modelled here¶

    To be direct about the gap between the physical picture in §4.1 and the implemented model in §4.3: this project's comet_profile is a phenomenological curve fit chosen because it matches the qualitative fast-fade/slow-recovery shape and is analytically tractable to fit by least squares — it is not derived from first-principles dust-tail radiative transfer, orbital mechanics, or an assumed tail composition/density profile. The gap between "a curve shaped like what we expect" and "a curve derived from comet physics" is exactly what Next Steps items F2/J5 (a physical forward simulator) are meant to close, and it is currently open. PLANNED, NOT IMPLEMENTED.
