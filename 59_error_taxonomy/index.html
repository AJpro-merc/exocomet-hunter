    59. Error Taxonomy¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    Real error classes actually hit during this project's development, each with cause, detection, recovery, and known test coverage. Machine-readable mirror: docs/specification/registry/errors.yaml.

    ERR-001 — MastTimeoutError¶

    • Class: exocomet.io.download.MastTimeoutError (subclasses TimeoutError).
    • Cause: A MAST network call (search_lightcurve or download_all) stalls on a socket that never returns, with no deadline. Root-caused 2026-09-15: a fetch for KIC 3542116 sat at zero CPU for nine minutes and had to be killed, twice, before bounded timeouts existed.
    • Detection: _call_with_timeout() runs the call on a daemon thread and raises MastTimeoutError if the thread is still alive after search_timeout/download_timeout seconds (60s / 300s defaults).
    • Recovery: _call_with_retries() retries up to DEFAULT_MAX_ATTEMPTS (3) times with exponential backoff (5s, 10s), optionally running a cleanup callback between attempts (see ERR-002). iter_light_curves() additionally enforces a hard per-target wall-clock budget (DEFAULT_TARGET_BUDGET, 900s) so one hung star cannot stall an entire batch.
    • Known limitation: the daemon thread itself cannot be cancelled — an abandoned thread may still be alive holding a socket after the caller stops waiting; the module docstring states this honestly ("this bounds how long the caller waits," not the underlying resource).
    • Test coverage: tests/unit/test_download_timeout.py.
    • Status: IMPLEMENTED, TESTED, VALIDATED (the fix's root cause was independently re-confirmed live: the same hang reproduced in 31 seconds instead of 9 minutes once the timeout was in place, revealing the true underlying cause — ERR-002).

    ERR-002 — Poisoned-cache retry (truncated FITS file)¶

    • Class: Not a distinct exception type — surfaces as a lightkurve/astropy error containing "may be corrupt due to an interrupted download," wrapped by the ERR-001 retry machinery.
    • Cause: A download interrupted partway leaves a truncated FITS file cached on disk (observed twice: 2026-09-15, exactly 65536 bytes — a round 64 KiB block boundary, the signature of a kill mid-transfer; and again 2026-09-16 for a different star during live scripts/ingest.py testing). lightkurve/astropy finds the file already present at its cache path and does not know it is broken.
    • Detection: No proactive detection — discovered only when a subsequent read of the cached file fails with the "may be corrupt" error.
    • Recovery: Before 2026-09-15, none — a retry against the same poisoned cache failed identically every time, meaning "retry" was not actually retrying anything. Fixed by giving _call_with_retries() an optional cleanup callback, wired at the download_all call site to _discard_cached(cache, target_id) between attempts, so a retry now genuinely re-fetches rather than re-reading the same broken file.
    • Test coverage: No dedicated unit test simulating a truncated cache file was found; the fix is validated by direct observation (re-tested against the same failing target after the fix: clean success, per Session Log 2026-09-15 §11) rather than by an automated regression test.
    • Status: IMPLEMENTED, VALIDATED by direct observation; TESTED — NO (automated coverage gap).

    ERR-003 — Ledger false-success (a ledger line claiming success for a file that doesn't exist)¶

    • Class: Not a distinct exception; a data-integrity bug in the caller, not the ledger module itself.
    • Cause: A first real single-target test (KIC 1161345) printed "1 succeeded" but the extract file was missing from disk afterward. Root cause traced to ERR-002 above (a live recurrence of the truncated-cache corruption for a different star), not a bug in io/ledger.py — the ledger correctly recorded what it was told, but the caller's retry logic was the actual point of failure.
    • Detection: Not reproducible by directly calling process_one_target() in isolation nor via the CLI script alone — only reproduced on a third real attempt against live MAST.
    • Recovery: Fixed at the root (ERR-002's cleanup callback). Additionally, scripts/ingest.py::process_one_target() now has a belt-and-braces immediate readback check right after save_extract(): if not ex_path.exists(): raise RuntimeError(...), explicitly so this exact failure mode "can never recur silently even if some other cause produces it later" (function docstring).
    • Test coverage: The readback check itself is straightforward source-verifiable logic (line ~268–274 of scripts/ingest.py); no test was found that specifically simulates save_extract silently failing to produce the claimed file.
    • Status: IMPLEMENTED (defensive check), VALIDATED by direct observation of the fix; TESTED — NO (no dedicated regression test for this exact scenario).

    ERR-004 — CWD-relative cache path¶

    • Class: Not a distinct exception; a silent-wrong-behavior bug (no error raised at all).
    • Cause: DEFAULT_CACHE_DIR = Path("data/raw") in io/download.py is relative to the process's current working directory. Running scripts/ingest.py from inside scripts/ (matching sibling scripts' own convention) silently created scripts/data/raw/ instead of the repo-root cache the rest of the codebase assumes — flagged as a known risk earlier in the same session ("not trivially safe to change") before it actually manifested.
    • Detection: Found by direct observation during real MAST testing, not by an automated check.
    • Recovery: scripts/ingest.py::process_one_target() now computes an explicit raw_cache_dir from Path(__file__).resolve().parent.parent / "data" / "raw", independent of the process's CWD, and passes it into fetch_light_curve() rather than relying on the library default. Note: io/download.py's own DEFAULT_CACHE_DIR module constant is itself unchanged and still CWD-relative — the fix is local to ingest.py's call site, not a change to the shared default. Any future caller of fetch_light_curve()/iter_light_curves() that does not pass an explicit cache_dir can still hit this same bug.
    • Test coverage: No test found asserting cache-directory resolution is CWD-independent.
    • Status: PARTIAL — fixed at the one call site known to have hit it (scripts/ingest.py); the underlying CWD-relative default in io/download.py remains, so this is a mitigated instance of a still-latent design issue, not a closed one. TESTED — NO.

    ERR-005 — _discard_cached silently matching nothing (a no-op disguised as success)¶

    • Class: Not a distinct exception; a silent-wrong-behavior bug.
    • Cause: An earlier version of _discard_cached() matched a normalized slug of target_id against lightkurve's own pipeline-internal cache directory names — which never contain the catalog string a caller searched with (a Kepler product directory is named after Kepler's own zero-padded ID, kplr001161345_lc_..., with no "kic" anywhere; a TESS HLSP product embeds a zero-padded TIC number, unrelated to a resolved common name like "beta Pic"). The match therefore matched nothing, for any target, on either mission. discard_after_read=True had silently been a no-op since it was written — found 2026-09-14 when 166 MB of "already discarded" downloads had actually accumulated on disk.
    • Detection: Direct disk-usage inspection, not an automated check.
    • Recovery: _discard_cached() now wipes the entire mastDownload tree under the cache directory rather than attempting to match a specific target's subdirectory — correct as long as targets are processed one at a time (true of every current caller as of this commit: iter_light_curves, scripts/monitor_new_data.py, MastLightCurveSource). The function's own docstring notes a future parallel-worker batch (Next Steps E4) would need per-target cache subdirectories instead of this blunter approach.
    • Test coverage: UNVERIFIED — not confirmed whether a test asserts the cache tree is actually removed after a call.
    • Status: IMPLEMENTED, VALIDATED by direct observation (166 MB accumulation before, confirmed cleanup after).

    ERR-006 — Permanent vs. retryable failure conflation (bad KIC identifiers)¶

    • Class: FileNotFoundError (raised by fetch_light_curve() when a MAST search returns zero products).
    • Cause: Five hand-curated KIC identifiers in KEPLER_HOST_STARS (never validated against a real catalog when the list was hand-curated, 2026-09-14) do not correspond to any real Kepler observation. Found live 2026-09-16: each failed identically across two separate hourly ingest.yml runs, six hours apart, with "Could not resolve ... to a sky position," each time burning the whole per-run target budget on nothing and failing the job outright, which also skipped the downstream TESS job (needs: kepler in ingest.yml).
    • Detection: Live observation of repeated identical failures across independent runs.
    • Recovery, two-part: (1) scripts/build_kepler_host_list.py removed the five bad IDs (KIC 1571512, 3735741, 3839966, 4457741, 4569375) from KEPLER_HOST_STARS outright, distinct from KNOWN_BAD_HOSTS since these simply do not exist as observed targets rather than having a real astrophysical reason to exclude. (2) scripts/ingest.py::run_ingest() now recognizes FileNotFoundError specifically as a permanent failure (is_permanent = isinstance(exc, FileNotFoundError)) and records it at attempt=max_attempts immediately — one ledger line, not max_attempts of them — so next_targets() excludes it from all future runs instead of re-selecting it forever.
    • Test coverage: UNVERIFIED whether tests/unit/test_ingest.py specifically exercises the permanent-vs-retryable distinction (it does test general failure recording, per Next Steps B6/§44.2 REQ-FUNC-004).
    • Status: PARTIAL — the fix exists only in the local working tree, NOT YET COMMITTED as of HEAD 01c2051. Direct inspection of git status/git diff confirms scripts/ingest.py's is_permanent/recorded_attempt logic and scripts/build_kepler_host_list.py's removal of the five bad KIC IDs are both uncommitted local modifications on top of 01c2051, not part of that commit. This is corroborated by real live evidence: 23_automation.md §23.2 (querying gh run list directly on 2026-09-16) shows the two most recent scheduled ingest runs (2026-09-16T00:05:07Z and 2026-09-16T05:50:28Z) both failed, in ~1 minute each — consistent with the committed (unfixed) code still hitting this exact bug in production, since those runs necessarily ran against 01c2051 as pushed, not the working-tree fix. The fix described above is real code that exists on this machine, but has not yet reached the live pipeline.
