    9. Software Architecture¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    9.1 Design philosophy: framework over script¶

    Stated directly in the README: "The package is a framework, not a script." The concrete mechanism is a set of abstract interfaces in core/interfaces.py that the rest of the pipeline is written against, rather than against the exocomet detector specifically — the module's own docstring: "A different search — for example the planned anomalous-dimming (technosignature) detector — is added by implementing Detector and passing it to exocomet.pipeline.run_target; no orchestration code changes." (Note: exocomet.pipeline.run_target is the docstring's own forward reference to planned orchestration — see §9.5; it does not exist yet as of this commit.)

    9.2 The four interfaces, with their real method signatures¶

    All four live in src/exocomet/core/interfaces.py.

    LightCurveSource (typing.Protocol, @runtime_checkable): 

    def fetch(self, target_id: str, mission: str) -> LightCurveData: ...
    Implemented by MastLightCurveSource (io/download.py).

    Detrender (Protocol, @runtime_checkable): 

    def detrend(self, lc: LightCurveData) -> LightCurveData: ...
    Implemented by SavGolDetrender and SplineDetrender (detrend/detrend.py), each wrapping the corresponding module-level function (detrend_savgol, detrend_spline).

    Vetter (Protocol, @runtime_checkable): 

    def vet(self, event: DipEvent, lc: LightCurveData) -> VettingResult: ...
    No concrete implementation exists. vetting/__init__.py is an empty module (docstring only). NOT IMPLEMENTED.

    Detector (abc.ABC): 

    class Detector(ABC):
    name: str = "detector"

    @abstractmethod
    def detect(self, lc: LightCurveData) -> list[DipEvent]: ...

    @abstractmethod
    def score(self, event: DipEvent, lc: LightCurveData) -> EventScore: ...

    def run(self, lc: LightCurveData) -> list[CandidateRecord]:
        return [CandidateRecord(event=event, score=self.score(event, lc)) for event in self.detect(lc)]
    The class docstring frames the split deliberately: "A detector answers two questions: which parts of a light curve look like events (detect), and how confident we are that a given event is real (score). Splitting the two keeps the expensive statistical work off the path of the cheap first pass." The base run() implementation is a naive detect-then-score loop; concrete subclasses may override it for efficiency (see §9.3 — AsymmetricDipDetector.run does exactly this).

    9.3 The one concrete detector: AsymmetricDipDetector¶

    detect/comet_detector.py. Its own module docstring states its scope precisely: "This class is deliberately thin. It owns no science of its own; it sequences the baseline estimation, candidate finding, geometric measurement and statistical scoring implemented in the sibling modules." Concretely:

    • baseline_and_noise(lc) — converts BaselineConfig.median_window_days/noise_window_days to cadence counts via days_to_cadences (using that light curve's own measured cadence_days) and calls rolling_baseline/local_noise (detect/baseline.py).
    • detect(lc) — calls find_candidate_events (detect/candidates.py) then measure_event (detect/asymmetry.py) per window. Events whose ingress or egress could not be fitted are still returned, carrying unmeasurable_reason, rather than silently vanishing.
    • score(event, lc) — recomputes the baseline (again, since score may be called independently of detect) and calls score_event (detect/scoring.py).
    • run(lc) — overrides the base Detector.run, computing the baseline and the Lomb-Scargle periodogram once per light curve rather than once per event, since both are properties of the whole series, not of one event. This is the method actually used by every real caller (cli.py, scripts/ingest.py).

    A fixed RNG (np.random.default_rng(self.config.runtime.rng_seed), default seed 42) is instantiated once per detector instance and reused across the bootstrap significance draws in score_event, so results are reproducible run-to-run for identical input data and config.

    9.4 Repository structure¶

    src/exocomet/
  core/        — types.py, config.py, interfaces.py (no dependency on lightkurve/archive APIs)
  io/          — download.py (MAST only), extract.py (parquet), ledger.py (JSONL)
  detrend/     — detrend.py (Savitzky-Golay / spline)
  detect/      — baseline.py, candidates.py, asymmetry.py, model_comparison.py, scoring.py, comet_detector.py
  calibration/ — injection.py, features.py (synthetic injection-recovery, classifier features)
  vetting/     — empty (NOT IMPLEMENTED, see 09.2/09.5)
  viz/         — plots.py
  cli.py       — `exocomet` console script

scripts/       — ingest.py, build_local_db.py, build_target_list.py, build_kepler_host_list.py,
                 generate_training_labels.py, train_classifier.py, run_validation.py,
                 measure_depth_offset.py, monitor_new_data.py, vet_host_list.py
config/        — thresholds.yaml, validation_targets.yaml, watchlist.txt, tess_training_hosts.txt
docs/          — NEXT_STEPS.md, SESSION_LOG_*.md, research_log/, cloud-routine-prompt*.md, specification/ (this document)
tests/         — unit/, integration/, benchmarks/ (benchmarks currently an empty package, see Next Steps E7)
.github/workflows/ — ingest.yml, survey.yml (disabled), train.yml

    pyproject.toml declares the package under src/ layout ([tool.setuptools.packages.find] where = ["src"]), Python ≥3.11, and a single console-script entry point exocomet = "exocomet.cli:main".

    9.5 Future detector architecture: H4 (technosignature detector)¶

    Named directly in both the README ("the planned anomalous-dimming (technosignature) detector") and Next Steps item H4: "Project 2 — technosignature / anomalous dimming. New Detector subclass (Isolation Forest on light-curve features), validated on Boyajian's Star (KIC 8462852), reusing io/, detrend/, core/, vetting/." PLANNED. NOT IMPLEMENTED. No code toward this exists in src/exocomet/ as of this commit — it is cited here specifically because it is the concrete test case the Detector ABC's plugin design (§9.1–9.2) is meant to prove out: adding this detector should require writing one new class, not modifying core/, io/, or detrend/. Whether that claim holds has not yet been tested, since H4 has not been attempted.
