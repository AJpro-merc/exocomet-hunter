    6. Data Sources¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    6.1 NASA Kepler and TESS¶

    Kepler. Long-cadence photometry at 29.4 minutes. This exact figure is load-bearing in this codebase: Next Steps item A1 ("Window sizes are counted in measurements, not in time," ✅ done 2026-09-14) records that every window in config/thresholds.yaml was originally chosen in units of Kepler long-cadence measurements, and had to be converted to physical time (days) once TESS data — sampled at wildly different rates — entered the pipeline. LightCurveData.cadence_days (core/types.py) is measured per light curve, not assumed, as the median of np.diff(time).

    TESS. SPOC pipeline products at 120 s (the standard 2-minute cadence) and 20 s; Full-Frame-Image (FFI)-derived products at 200 s, 600 s, and 1800 s depending on which TESS extended-mission phase produced them. Verified directly against real MAST queries during the A1 investigation: at 120 s cadence, the (then Kepler-tuned) 401-cadence detrend window worked out to 13.4 hours; at 20 s cadence, the same 401-cadence window was only 2.2 hours — both far too short relative to the ~1-day comet dips this project is looking for, which is exactly what motivated converting every window to a days-based config (DetrendConfig.window_days, BaselineConfig.median_window_days, etc. — see 10_configuration.md).

    Both missions are accessed exclusively through the single io/download.py module — "Only this module knows about lightkurve" (module docstring) — so the rest of the pipeline operates on LightCurveData without caring which mission or pipeline produced it.

    6.2 MAST, and how io/download.py actually queries it¶

    fetch_light_curve (io/download.py) wraps lightkurve.search_lightcurve(...).download_all(...).stitch(). Two real, documented problems and their fixes govern how this query is actually constructed (both closed under Next Steps item A2, "TESS products from different pipelines get stitched together," ✅ done 2026-09-14):

    Author/exptime pinning. A plain lk.search_lightcurve(target, mission="TESS") can return dozens of products from different pipelines (QLP, SPOC, TARS, TASOC, TESS-SPOC, TGLC) at cadences from 20 s to 1800 s. Blindly stitching all of them caused two distinct real problems (found and fixed 2026-09-14, per the module's own "Notes" docstring on fetch_light_curve): (1) a detrending/baseline window sized for one cadence is a wildly wrong physical duration at another; (2) at least one HLSP pipeline (TARS) reports flux as an already zero-centred residual rather than raw counts, so stitching it in could divide by a near-zero median and corrupt normalisation outright. The fix: fetch_light_curve now defaults to author="SPOC", exptime=120 for TESS and author="Kepler" for Kepler/K2, pinning to a single pipeline rather than only separating by cadence. Verified against real data (Next Steps A2): β Pic resolved to 10 clean SPOC/120s products, down from 54 mixed-pipeline products, with flux normalising to a sane 0.99–1.01 range.

    Bounded network calls. Every MAST call (search_lightcurve, download_all) runs on a daemon thread with an explicit wall-clock timeout (DEFAULT_SEARCH_TIMEOUT=60s, DEFAULT_DOWNLOAD_TIMEOUT=300s) and bounded retries (DEFAULT_MAX_ATTEMPTS=3, exponential backoff from DEFAULT_RETRY_BACKOFF=5s), raising MastTimeoutError (subclasses TimeoutError) rather than blocking indefinitely. The module docstring records why this exists as a hard requirement, not a nicety: "a fetch for KIC 3542116 sat at zero CPU for nine minutes and had to be killed, twice," even though the underlying files had already fully downloaded — the process was blocked on a socket with no deadline. A related, separately-fixed bug: a retry against a poisoned local cache (a FITS file left truncated by an earlier interrupted download) would fail identically every time unless the corrupt cache entry was cleaned up between attempts — _call_with_retries's cleanup callback exists specifically for this (see 35_code_reference/io.md for the exact mechanism).

    Stream-and-discard. discard_after_read=True deletes the cached mastDownload tree for a target immediately after its arrays are extracted, so the local working set stays at a few megabytes regardless of how many stars are processed (README: "Light curves are streamed and discarded by default"). This exact behaviour was, for a period, a silent no-op — see 07_data_architecture.md §7.3 and 08_storage.md for the specific bug and fix (Findings Log, 2026-09-14).

    6.3 NASA Exoplanet Archive and VizieR¶

    VizieR is IMPLEMENTED as a real query target: scripts/build_target_list.py pulls a published, vetted debris-disc catalogue — Cotten & Song (2016), ApJS 225, 15, VizieR id J/ApJS/225/15, "A Uniformly Vetted Compilation of Debris Disk Candidates" — chosen specifically because it is already literature-cross-checked rather than a raw infrared-excess catalogue needing its own vetting pass (script's own module docstring). It cross-matches each disc star's sky position against the TESS Input Catalog (astroquery.mast.Catalogs) to resolve TIC/KIC identifiers, confirms real downloadable photometry exists via the same lightkurve search machinery used elsewhere, and selects a magnitude-matched control star per disc star (for the planned debris-disc-vs-control comparison, Next Steps F4).

    However, per Next Steps item 3 ("FIRST THING NEXT SESSION"), build_target_list.py's control-group matching is currently broken — "it queries VizieR/TIC for real and returns disc-star matches, but the matched-control step returns zero matches, so it produces no output files" — and its output is not yet wired into scripts/ingest.py's target sources. ingest.py currently runs against the 33 hardcoded seed targets (23 Kepler + 10 TESS) only (get_target_list(), scripts/ingest.py). PARTIAL.

    NASA Exoplanet Archive is named in the README's "Data sources" list ("target and cross-match data from... the NASA Exoplanet Archive") but no code in src/exocomet/ or scripts/ queries it as of this commit. NOT IMPLEMENTED — this appears to be an aspirational/planned data source stated in the README rather than a currently-exercised one; readers should not assume Exoplanet Archive data has been cross-matched into any current target list or result.

    6.4 SIMBAD and Gaia¶

    Both are listed in the README's "Data sources" section ("Kepler/TESS photometry from MAST; target and cross-match data from the NASA Exoplanet Archive, VizieR, SIMBAD and the Gaia archive"). Neither is implemented. src/exocomet/vetting/__init__.py — the module that would house SIMBAD object-type lookups and Gaia stellar-parameter cross-matching, per Next Steps item D2's own description of the planned module contents (catalogs.py: "SIMBAD object type (astroquery.simbad), AAVSO VSX variable flag, Kepler/TESS eclipsing-binary catalogue membership, Gaia parameters") — currently contains only a module docstring and no functions, classes, or imports:

    """Catalogue cross-matching and false-positive checks."""

    NOT IMPLEMENTED. No astroquery.simbad or Gaia-archive import exists anywhere in src/exocomet/. This is a real gap between the README's stated data sources and the current code, not a subtle distinction — anyone relying on this document to understand what vetting has actually run against a candidate should read this as: no catalogue cross-match vetting has been performed on any candidate this pipeline has produced, as of this commit.
