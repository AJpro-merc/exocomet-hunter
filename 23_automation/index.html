    23. Automation (GitHub Actions)¶

    Status: reflects the live GitHub Actions state as queried directly via gh workflow list --all and gh run list on 2026-09-16, plus direct reads of all three workflow YAML files in the working tree. This is real-time infrastructure state, not a static code artifact — re-verify with the same commands before relying on this section for anything operational.

    23.3 ingest.yml — the active workflow¶

    Two sequenced jobs, kepler then tess (needs: kepler), each timeout-minutes: 45. Trigger: cron: "0 * * * *" (hourly) plus workflow_dispatch with optional time_budget_minutes (default "25") and max_targets inputs. concurrency: {group: ingest, cancel-in-progress: false} — a second trigger queues rather than running in parallel, matching scripts/ingest.py's own documented concurrency assumption (11_pipeline.md §11.7).

    Each job: checkout → setup Python 3.12 → pip install -e ".[dev]" → clone AJpro-merc/exocomet-hunter-data (using secrets.DATA_REPO_TOKEN, over HTTPS with an x-access-token credential) into data-repo/ → run scripts/ingest.py --mission {Kepler,TESS} --data-repo-dir data-repo --time-budget-minutes ... → pytest tests/unit -q → commit and push any new ledger/extract/results files back to the data repo, with git pull --rebase --autostash before pushing to handle a concurrent writer.

    Direct consequence of the sequenced needs: kepler: if the kepler job fails outright (as it did in both 2026-09-16 failures, per §23.2), the tess job never runs at all for that hourly cycle — this is the specific mechanism by which the five-bad-KIC-ID bug also silently starved TESS ingestion, not only Kepler, on both occasions.

    All output (ledger.jsonl, extract/, results/) is pushed to the separate AJpro-merc/exocomet-hunter-data repository, never to this repo's own git history — matching scripts/ingest.py's module docstring layout description (11_pipeline.md §11.1).

    23.4 survey.yml — disabled, older/separate pipeline¶

    Verified disabled_manually. This is a distinct, older pipeline (scripts/monitor_new_data.py) with its own state file (results/processed_ledger.json, a whole-file-rewrite pattern — not the append-only JSONL ledger io/ledger.py implements for ingest.py). Scheduled daily at 0 5 * * * when active, capped to a handful of targets per run via --limit (default 5), watching config/watchlist.txt for new TESS sectors. Commits results directly to this repository (not the separate data repo), unlike ingest.yml. Session Log 2026-09-15 §5 records the disable reason: gh run list showed train.yml burning ~2h16m of real compute across four consecutive failures producing zero output, traced to the scheduled trigger referencing a stale pre-force-push commit SHA after a history-cleaning force-push orphaned it; both survey.yml and train.yml were disabled together pending a real commit to re-anchor main. This document's own gh workflow list --all query independently confirms both remain disabled as of 2026-09-16 — this is not merely a historical claim carried forward from the session log.

    23.5 train.yml — disabled, classifier training pipeline¶

    Verified disabled_manually. Two cron schedules in one workflow: 0 */2 * * * (generation — kepler/tess jobs run scripts/generate_training_labels.py, capped at --max-new-rows 400, --bootstrap-draws 300, writing labelled parquet rows to the data repo) and 0 6 * * 1 (weekly retrain — the train job, gated if: always() && (...), runs scripts/train_classifier.py against whatever accumulated data exists, skipping a mission's refit if its data's SHA-256 hash is unchanged since the last run). The workflow's own top-of-file comment explains why generation and training are split this way rather than combined, and why this runs on GitHub Actions rather than a Claude Cloud routine: "Claude Cloud routines cannot reach mast.stsci.edu (a 403 from the sandbox's own egress proxy, confirmed 2026-09-14)." Both jobs, like ingest.yml, push results to AJpro-merc/exocomet-hunter-data using the same DATA_REPO_TOKEN secret.

    docs/NEXT_STEPS.md (working tree) lists re-enabling train.yml as downstream of ingest.yml running unattended successfully; as of this document neither train.yml nor survey.yml has been re-enabled since the 2026-09-15 disable.

    23.6 DATA_REPO_TOKEN¶

    Per Session Log 2026-09-15 §12, this secret was added by the repository owner after the session that built ingest.py, and a subsequent live workflow_dispatch run confirmed the full ingest cycle (fetch → extract → detrend → detect → save results → push) succeeding end-to-end on GitHub's own infrastructure, with files independently verified to land in exocomet-hunter-data via the GitHub API. This document did not re-verify the token's presence directly (no gh secret list permission was exercised during this review), but the run history in §23.2 — specifically the two successful ingest runs on 2026-09-15 — is consistent with the token being present and working prior to the unrelated five-bad-KIC-ID regression that then caused the two subsequent failures on 2026-09-16.
