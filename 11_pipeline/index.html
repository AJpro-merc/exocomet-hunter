    11. Pipeline Overview¶

    Status: reflects repo state as of 2026-09-16. Git HEAD is commit 01c2051. The working tree at the time this was written also carries uncommitted changes to scripts/ingest.py and scripts/build_kepler_host_list.py (verified via git diff) that fix a live bug found the same day; this section describes the code as it currently sits on disk, and calls out the uncommitted status explicitly wherever it matters. IMPLEMENTED / TESTED (offline unit tests) / OPERATIONAL (one real GitHub Actions run confirmed end-to-end, verified live against AJpro-merc/exocomet-hunter-data).

    11.1 What "the pipeline" means here¶

    There are two related things called "the pipeline" in this codebase and it matters which one a given section is about:

    1. The detection pipeline — detrend → find candidates → measure asymmetry → score (detrend_savgol, find_candidate_events, measure_event, score_event). Pure computation on an in-memory LightCurveData; no I/O of its own. See 12_acquisition.md through 17_uncertainty.md.
    2. The ingestion pipeline (scripts/ingest.py) — the resumable, hourly-run orchestration that fetches a target, runs the detection pipeline on it, and durably records the outcome. This section is about the ingestion pipeline.

    11.2 The six-step per-target sequence¶

    scripts/ingest.py's process_one_target() (lines 214–316) performs exactly six steps, in this order, per the module's own docstring (lines 9–24):

    1. Fetch the light curve from MAST (exocomet.io.download.fetch_light_curve). Raw FITS files land on local disk; nothing is deleted yet.
    2. Save the extract to disk, atomically (exocomet.io.extract.save_extract) — the permanent, detector-independent time/flux/flux_err arrays as a parquet file at extract/<mission>/<target>.parquet.
    3. Only now, delete the raw FITS (shutil.rmtree(raw_cache_dir / "mastDownload", ...)).
    4. Run the existing detection pipeline (detrend_savgol then AsymmetricDipDetector(config).run(detrended)) on the extract.
    5. Write the results file, atomically (_write_results_jsonl), one JSON line per CandidateRecord.to_row(), at results/<mission>/<target>.jsonl. Written even when there are zero candidates — an empty file is retained as meaningful evidence that the star was processed and found quiet, distinct from "never attempted."
    6. Only now, append one ledger line recording success (exocomet.io.ledger.append_entry, status="success").

    11.3 Why this exact order is the safety mechanism¶

    Quoting the module docstring directly (scripts/ingest.py lines 19–24):

    If the process is killed anywhere before step 6, no ledger entry exists for this attempt, so the target is simply retried next run — save_extract and the results write are both themselves atomic, so a killed run never leaves a half-written extract or results file behind, only (at worst) a missing one. The ledger line is written last, deliberately, so it can never claim success for work that did not fully land.

    This was a real design decision, not an incidental ordering choice, driven by the GitHub Actions execution environment: ingest.yml runs on a 45-minute timeout-minutes budget and the runner can be killed by GitHub at any point with no graceful-shutdown guarantee. run_ingest() checks the time budget once per target, at the top of the loop (gating whether to start another target, never interrupting one already in flight) — a star is the atomic unit of work.

    Concrete failure mode this ordering prevents: if the ledger were written before detection ran (or before the extract was durably saved), a runner killed mid-detection would leave a ledger entry claiming status="success" for a target with no results file and possibly no extract — a permanent, silent lie in the source of truth that no later run would ever notice or correct, because next_targets() (see 11.5) would treat that target as done.

    Both save_extract (io/extract.py lines 82–125) and _write_results_jsonl (scripts/ingest.py lines 188–211) achieve their own atomicity the same way: write to a temporary file in the same directory, then os.replace() into the final path (atomic on POSIX, which covers both GitHub Actions runners and macOS). A reader can therefore only ever observe the final path as completely absent or completely written.

    11.4 A real, verified bug this ordering did not prevent (but a nearby check did)¶

    Session Log 2026-09-15 §11 records a live-tested failure mode: process_one_target printed "1 succeeded" but the extract file was missing from disk afterward on the first real MAST test. Root cause traced to _call_with_retries (io/download.py) retrying download_all against a poisoned local cache with no cleanup between attempts — not a bug in the six-step ordering itself, but in a lower layer. Two fixes landed as a result: _call_with_retries gained a cleanup callback wired to _discard_cached() between attempts (io/download.py lines 161–207, 412), and ingest.py added a belt-and-braces immediate readback check right after save_extract (lines 268–274) — a ledger entry claiming success for output that is not actually on disk is treated as unreachable-but-checked-anyway, per the code comment:

    a ledger entry claiming success for a file that isn't actually there is a worse failure mode than a loud, immediate one, so it's checked directly rather than trusted.

    11.5 Failure recovery: the ledger's resume logic¶

    State lives entirely in <data-repo-dir>/ledger.jsonl, an append-only JSON-lines file (exocomet.io.ledger). Two functions drive resumability:

    • latest_entries(entries) (lines 165–177) — reduces the full, chronological ledger to one entry per (target_id, mission) key: the last entry seen wins. This is "current status per target."
    • next_targets(ledger_path, all_targets, mission, max_attempts=3) (lines 197–241) — returns exactly the targets that still need processing:
    • Never-attempted targets, in the order given in all_targets — first, so a bounded run spends its budget on fresh ground before retries.
    • Then retriable failures (status="failed" and attempt < max_attempts), oldest-failure-first by timestamp_utc — so one flaky target being retried repeatedly cannot starve an older failure.
    • Excluded entirely: targets whose latest entry is status="success", or whose latest entry is status="failed" with attempt >= max_attempts (exhausted).

    run_ingest() (scripts/ingest.py lines 318–421) calls next_targets() at the start of each mission's run, then processes targets[:max_targets] within the time budget. On any exception, it writes a status="failed" ledger entry and continues to the next target — one bad star never kills the run (except Exception as exc: # noqa: BLE001, line 382).

    11.6 The 2026-09-16 permanent-failure fix (uncommitted at time of writing)¶

    This is the live bug referenced by the task brief, and it is present in the working tree but not yet in git history (git status shows scripts/ingest.py and scripts/build_kepler_host_list.py as modified, uncommitted, on top of 01c2051).

    The bug: KEPLER_HOST_STARS (the hardcoded Kepler target tuple) previously contained five KIC identifiers — KIC 1571512, 3735741, 3839966, 4457741, 4569375 — that do not correspond to any real Kepler observation. Session Log 2026-09-15 §9 already notes the list "was never checked against a real catalog when it was hand-curated" (the same root cause as the earlier KIC 1026032 removal). fetch_light_curve() raises FileNotFoundError for such a target (io/download.py lines 392–396, "no products for this target"). Before the fix, run_ingest()'s exception handler recorded this the same way as any other failure — one ledger entry per attempt, attempt incremented each time — so next_targets() kept re-selecting these five targets on every hourly run until max_attempts (default 3) was reached, burning the whole per-run target budget on targets that can never succeed, and (because the kepler job's failure blocked the sequenced tess job via needs: kepler in ingest.yml) skipping TESS ingestion entirely. gh run list (see 23_automation.md) shows two real ingest runs failing this way six hours apart on 2026-09-16.

    The fix (scripts/ingest.py lines 382–419, current working-tree state): the exception handler now distinguishes FileNotFoundError — "the MAST search itself returned zero results ... not a transient network issue" — from every other exception. When isinstance(exc, FileNotFoundError), the ledger entry is written with attempt=max_attempts immediately, in one entry rather than accumulating one per run, so next_targets() excludes the target from every subsequent run without needing three real attempts to get there. The five bad IDs were also removed outright from KEPLER_HOST_STARS (scripts/build_kepler_host_list.py, working tree), reducing the Kepler host list from ~23 to 18 targets; they were not added to KNOWN_BAD_HOSTS (which is reserved for stars with real data and a real astrophysical reason for exclusion, e.g. KIC 1026032's eclipsing binary) because they simply do not exist as observed Kepler targets.

    11.7 Concurrency¶

    Two runs processing the same target simultaneously is prevented at the GitHub Actions level: ingest.yml sets concurrency: {group: ingest, cancel-in-progress: false}, which queues a second trigger rather than running it in parallel. There is no in-process lockfile in ingest.py itself — the module docstring states this is "simpler, and sufficient given the workflow already owns this guarantee."
