    12. Data Acquisition¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051 (this module is unmodified in the working tree's uncommitted diff). IMPLEMENTED / TESTED.

    All light-curve retrieval from MAST is confined to one module, src/exocomet/io/download.py (581 lines). Its own docstring states the design intent directly: "Only this module knows about lightkurve. Everything downstream operates on LightCurveData, so the science code neither knows nor cares where the photometry came from."

    12.1 Public surface¶

    • fetch_light_curve(target_id, mission="Kepler", cadence="long", author=None, exptime=None, cache_dir=DEFAULT_CACHE_DIR, discard_after_read=False, quality_bitmask="default", search_timeout=60.0, download_timeout=300.0, max_attempts=3, retry_backoff=5.0) -> LightCurveData (lines 285–433) — download, stitch and normalise all available photometry for one target.
    • iter_light_curves(target_ids, ..., discard_after_read=True, skip_errors=True, per_target_timeout=900.0, ...) -> Iterator[LightCurveData] (lines 468–541) — yields light curves one at a time, discarding each after it is consumed; the memory- and disk-safe way to process a large target list.
    • MastLightCurveSource (lines 544–581) — a thin class wrapper satisfying the LightCurveSource protocol in core/interfaces.py, delegating to fetch_light_curve.
    • MastTimeoutError(TimeoutError) (lines 85–91) — raised when a MAST network call exceeds its wall-clock budget. Subclasses TimeoutError so existing except OSError / except Exception handlers keep working unchanged.

    12.2 Target selection and pinning (the A2 fix)¶

    fetch_light_curve pins a single pipeline (author) and, for TESS, a single exposure time (exptime), rather than accepting whatever lightkurve finds:

    • Kepler/K2: author defaults to "Kepler"; cadence ("long" or "short") is passed through.
    • TESS: author defaults to "SPOC", exptime defaults to 120 (seconds).

    This exists because of a real, documented problem (module docstring, lines 353–364, "Next Steps A2"): a plain lk.search_lightcurve(target, mission="TESS") can return dozens of products from different pipelines (QLP, SPOC, TARS, TASOC, TESS-SPOC, TGLC, ...) at cadences from 20 s to 1800 s. Blindly stitching all of them together caused two distinct, separately-found problems:

    1. A detrending/baseline window sized for one cadence is a wildly wrong physical duration at another (see 13_detrending.md, A1).
    2. At least one HLSP pipeline (TARS) reports flux as an already zero-centered residual rather than raw counts, so stitching it in could divide by a near-zero median and corrupt the normalisation outright.

    Pinning to a single author/exptime avoids both at once.

    12.3 Timeout and retry behaviour (the 2026-09-15 hardening)¶

    Before 2026-09-15, no MAST call in this module had a wall-clock bound. The module docstring records the concrete incident that motivated the change: a fetch for KIC 3542116 sat at zero CPU for nine minutes and had to be killed, twice, even though the 17 FITS files already in the cache were all complete and written within one minute — "the process was blocked on a socket that never returned and had no deadline to hit."

    The fix layers three independent bounds:

    • _call_with_timeout(func, timeout, description) (lines 126–158) — runs func on a daemon thread and gives up waiting after timeout seconds, raising MastTimeoutError. A daemon thread is used deliberately, not concurrent.futures.ThreadPoolExecutor, because a stalled MAST socket cannot be cancelled from outside — the worker thread may still be alive when the caller stops waiting, and a daemon thread does not block interpreter exit the way a ThreadPoolExecutor (which joins its workers at shutdown) would. The documented honest limitation: this bounds how long the caller waits, not the orphaned thread's socket, which keeps holding it until astroquery's own timeout trips — which is why the next bound exists too.
    • _configure_astroquery(timeout=120.0, pagesize=5000) (lines 94–123) — pins astroquery.mast.conf.timeout/.pagesize and, best-effort, the private _portal_api_connection/_service_api_connection attributes (their names have moved across astroquery releases, so this degrades gracefully and never fails a download over it).
    • _call_with_retries(func, timeout, description, max_attempts=3, backoff=5.0, cleanup=None) (lines 161–207) — bounded retry (never infinite), exponential backoff (5 s, 10 s between attempts). The cleanup callback runs between failed attempts, added specifically because a download interrupted partway leaves a truncated FITS file cached on disk; simply calling download_all again does not fix it, because lightkurve finds the file already present at its cache path and does not know it is broken — "a retry with no cleanup is not actually a retry in that case, just the same failure repeated on a timer" (line 178–181). At the download_all call site this is wired to _discard_cached(cache, target_id).

    Documented budgets (module-level constants, lines 52–80):

    Constant Value Purpose
    DEFAULT_SEARCH_TIMEOUT 60.0 s catalogue query ceiling
    DEFAULT_DOWNLOAD_TIMEOUT 300.0 s bulk FITS fetch ceiling
    DEFAULT_MAX_ATTEMPTS 3 total attempts per network call (≤2 retries)
    DEFAULT_RETRY_BACKOFF 5.0 s base backoff, doubles each attempt
    DEFAULT_TARGET_BUDGET 900.0 s hard per-target ceiling in iter_light_curves
    ASTROQUERY_TIMEOUT 120.0 s per-HTTP-request socket timeout
    ASTROQUERY_PAGESIZE 5000 rows per astroquery page

    iter_light_curves's per_target_timeout (default 900 s) is the outer stop for a single hung star stalling an entire batch — before this existed, skip_errors could only skip a target that failed, not one that simply never returned. The documented residual risk: a target abandoned at per_target_timeout leaves its worker thread running, and if it later completes with discard_after_read=True it can wipe the shared mastDownload tree out from under the next target's download — "the blast radius is a redundant re-download rather than corrupt science" (lines 507–511).

    12.4 Light-curve representation¶

    fetch_light_curve returns LightCurveData (core/types.py, frozen dataclass):

    Field Type Meaning
    target_id str catalogue identifier, e.g. "KIC 3542116"
    mission str "Kepler", "K2", or "TESS"
    time FloatArray days (BKJD for Kepler, BTJD for TESS), strictly increasing
    flux FloatArray normalised so out-of-transit ≈ 1.0
    flux_err FloatArray per-cadence uncertainty, same normalised units
    meta dict[str, Any] free-form provenance

    __post_init__ (lines 66–77) validates array-length agreement, non-emptiness, and strictly-increasing time, raising ValueError otherwise. Derived properties: n_points, cadence_days (median of np.diff(time)), baseline_days (total time span). with_flux(flux, **meta) returns a copy with new flux and merged metadata — used by every detrending function.

    _to_light_curve_data() (lines 210–259) builds this from a stitched lightkurve object: drops non-finite time/flux/flux_err cadences, sorts by time, drops duplicate-timestamp cadences (logged — "a large count here is itself a sign that mismatched products ... got stitched together"), and normalises flux by its median (raising ValueError if the median is non-positive or non-finite). meta records n_dropped_nonfinite, n_dropped_duplicate_timestamp, median_raw_flux, source="MAST", plus n_products, author, exptime, sectors_or_quarters.

    12.5 Disk footprint: fetch-and-discard¶

    discard_after_read=True deletes the cached FITS tree (cache_dir/mastDownload) immediately after arrays are extracted, via _discard_cached() (lines 436–465). This wipes the entire mastDownload tree under cache_dir rather than matching a specific target's subdirectory — a deliberate choice documented at length: lightkurve names each product's cache directory after its own pipeline-internal identifier (e.g. kplr001161345_lc_...), never the catalog string a caller searched with, so matching a normalised slug of target_id against directory names is unreliable. An earlier version of this function did exactly that and matched nothing, for any target — discard_after_read had silently been a no-op since it was written, found 2026-09-14 when 166 MB of "already discarded" downloads had actually accumulated on disk. Wiping the whole tree is correct only as long as targets are processed one at a time, which is true of every current caller.

    12.6 Errors¶

    • FileNotFoundError — the archive returns zero products for this target, mission, author and exptime combination (line 392–396). This is the exception scripts/ingest.py treats as a permanent failure (see 11_pipeline.md §11.6).
    • MastTimeoutError — the catalogue query or bulk download exceeded its budget on every attempt.
