    31. Machine Learning¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051. This is the single most important accuracy checkpoint in this specification. The goal of PART C (Next Steps.md) is to replace the hand-set ΔBIC+τ/σ flagging rule (research log 007, detect/scoring.py) with a trained classifier, and to measure how good it is before trusting it. As of this commit, that measurement has never happened. Read this section literally — no accuracy, precision, recall, ROC-AUC, or any other classifier-quality number is stated anywhere below, because none exist.

    31.1 C1 — Labelled training set generator: BUILT — scripts/generate_training_labels.py¶

    Status: IMPLEMENTED.

    For each host star, the script downloads the light curve once (discard_after_read=True — raw photometry is never retained), then for each label class either injects a synthetic event or takes a real/time-reversed detection, runs the unmodified production detector (AsymmetricDipDetector) on it, and — if a matching candidate resulted — extracts its 19 features (calibration/features.py::FEATURE_NAMES) and records one labelled row.

    Seven classes, not the original five (confirmed directly from source, ALL_CLASSES in generate_training_labels.py):

    • comet, symmetric, reversed — localized asymmetric-dip shapes, matched to a specific injected epoch within match_tolerance_days.
    • flare — localized false-positive lookalike (Next Steps D1).
    • starspot — whole-light-curve sinusoidal modulation (period 0.5–30 d), matched to the nearest detection to a random anchor time rather than a single true epoch.
    • noise — no injection at all; a real detection on real, unmodified data.
    • time_reversed_real — a real light curve with flux reversed in time.

    Depth/amplitude sampling (DEPTH_GRID_PPM = (200, 300, 500, 750, 1000, 1500, 2000, 3000), weighted (1, 2, 3, 4, 4, 3, 2, 1)) is deliberately weighted toward the 500–2000 ppm region — the genuinely uncertain detection boundary — rather than sampled uniformly.

    Hard hold-out enforcement: EXCLUDED_HOLD_OUT_TARGETS (from build_kepler_host_list.py) is asserted absent from the host list before generation starts (assert not (set(hosts) & EXCLUDED_HOLD_OUT_TARGETS)), and the same list is checked again at load time in train_classifier.py (§31.2). KIC 3542116 and KIC 11084727 — the validation targets — must never appear in training data.

    A real bug found and fixed (2026-09-14): the generator originally never detrended before running the detector — every row generated before the fix ran on raw, undetrended flux. This was caught before anything untrustworthy had been committed anywhere, so no cleanup was needed, but it is a real, documented finding, not a hypothetical.

    Output: one row per detected event — 19 features (from FEATURE_NAMES) plus label, host_star, injected_depth, injected_tau_over_sigma, seed, author, exptime. Runs recurringly via .github/workflows/train.yml (GitHub Actions, every 2 hours) and by hand. Real accumulated output lives in the external AJpro-merc/exocomet-hunter-data repository (training/labels_kepler.parquet, training/labels_tess.parquet — see 33_results.md), not in this repository's git history.

    31.2 C2 — Train: BUILT — scripts/train_classifier.py¶

    Status: IMPLEMENTED, backtest status improved since the last recorded log entry — verify current claim below.

    Model: RandomForestClassifier (n_estimators=200, class_weight="balanced") wrapped in CalibratedClassifierCV (method="isotonic", cv=3). Confirmed directly from source: this is exactly what is implemented, no more and no less. HistGradientBoostingClassifier or a logistic-regression comparison model — mentioned in Next Steps as a possible "second model" — is not built.

    Binary target, not the original 5/7-class framing: y = (df["label"] == "comet").astype(int) — comet versus every other class collapsed into one negative class. This matches C4's eventual comet_probability output directly (a single probability of "is this a comet," not a multi-class label).

    Missing-value handling: SimpleImputer(strategy="median") plus an is_measurable indicator array appended per feature (_build_pipeline_inputs hstacks the imputed features with a same-shaped 0/1 "was this finite before imputation" matrix) — exactly as specified in Next Steps C2.

    Split by host star: GroupKFold on host_star, used only to produce out-of-fold (OOF) predictions for threshold selection and completeness measurement (train_and_cross_validate). The final saved model is refit on the full dataset after OOF predictions are computed — standard practice, and correctly distinguished in the code and its docstring from the OOF predictions themselves.

    Class imbalance: class_weight="balanced" on the underlying RandomForestClassifier.

    Calibrated probabilities: CalibratedClassifierCV, isotonic method, as specified.

    Hold-out enforcement — a hard exception, not a warning: load_labels() raises HoldOutError (a RuntimeError subclass) if either hold-out star's data is present in the input parquet files, and main() catches it, logs, and returns exit code 1 — training refuses to proceed rather than silently including hold-out data.

    Provenance: models/manifest_<mission>.jsonl (append-only) records row count, class counts (df["label"].value_counts()), host-star list, training_set_hash (SHA-256 over the input parquet bytes), package versions (exocomet, scikit-learn, pandas, numpy — via importlib.metadata.version, degrading to "unknown" rather than raising), the chosen threshold, and both backtest results described below. A models/last_compare.json optionally records a before/after comparison against the immediately preceding manifest entry — for visibility, explicitly not a gate: the code comment states the locked decision is "always commit, never silently withhold a worse model."

    The threshold itself is chosen from OOF negative-class scores at a fixed target false-positive rate: TARGET_FALSE_POSITIVE_RATE = 0.01 (1%), via np.quantile(negative_scores, 1.0 - 0.01). This is a real, implemented mechanism — but it is a training-time heuristic for picking a number, not the same thing as C3's "measure recall at 1% FPR" evaluation deliverable (§31.3). The threshold is selected using this rule; whether the resulting classifier's actual recall at that FPR is good has never been separately reported (that is exactly what C3 would do and has not done).

    Two backtests are wired into train_classifier.py and run automatically on every training run:

    1. real_data_backtest() — fetches the real KIC 3542116 light curve live (never trained on — enforced by load_labels's hard exception), matches its 6 published dips within the configured tolerance, extracts features for each matched candidate, scores it with the just-trained model, and reports how many of the 6 score above the chosen threshold. This is a real, functioning code path that requires live network access to MAST.
    2. completeness_by_depth() — uses the already-computed OOF predictions, grouped by injected_depth, to report the classifier's own recovery fraction versus injected depth (distinct from the hand-rule completeness table measured earlier in the project).

    On verification status: Next Steps.md (last updated 2026-09-16, the same date as this document) states C2 as "✅ built 2026-09-14, ⚠️ not fully verified", with the specific concern being that the real_data_backtest() network step hung for 9+ minutes and was killed before completing, in testing prior to the MAST-hang root-cause fix described in 29_reliability.md §29.1. That MAST-hang root cause (a truncated FITS file retried against a poisoned cache with no cleanup) has since been fixed and re-verified against live MAST data (Session Log 2026-09-15 §4, §11) — but that verification was performed inside ingest.py's fetch path, not inside a specifically-watched, complete run of train_classifier.py's real_data_backtest() function itself end-to-end with a real training set. No session log or manifest entry in this repository documents a completed, successful run of real_data_backtest() that produced a real backtest score. Until such a run is observed and recorded, this document treats C2's backtest step as: the underlying network-hang cause is fixed, but a full, successful, watched execution of this specific function has not been independently confirmed in any source read for this document. Status: IMPLEMENTED, UNVERIFIED (the specific concern from the last log entry is very likely resolved given the underlying root-cause fix, but no completed run of this exact function is documented anywhere read for this section — do not report a real-data-backtest score for KIC 3542116 as an established fact until a manifest entry containing one is found).

    31.3 C3 — Evaluate: NOT IMPLEMENTED, NO EVALUATION NUMBERS EXIST¶

    This is the deliverable that has not happened. State this plainly, because it is the easiest place in this entire specification to accidentally fabricate a number.

    Next Steps PART C, item C3 specifies exactly what must be produced:

    • ROC-AUC and precision-recall AUC (PR stated as mattering more, since comets are rare).
    • Recall at a fixed false-positive rate of 1%.
    • Confusion matrix across the classes.
    • A completeness curve versus injected depth and versus τ/σ, compared against the hand rule.
    • Permutation feature importance.
    • The "final exam": all 6 KIC 3542116 dips must score above the chosen threshold.
    • A write-up in docs/research_log/006-classifier-v1.md, including what failed.

    None of this exists. Specifically, verified by direct inspection:

    • No file named docs/research_log/006-classifier-v1.md exists. (docs/research_log/ contains exactly three files: 003-half-depth-contour-sign-error.md, 006-depth-offset-investigation.md, 007-delta-bic-is-direction-blind.md — note that 006 is already taken by the depth-offset investigation, a numbering collision with C3's proposed filename that would need resolving whenever C3 is actually written.)
    • No standalone ROC-AUC, PR-AUC, or "recall at 1% FPR" figure is reported anywhere in the codebase, the manifests, or any research log. The TARGET_FALSE_POSITIVE_RATE = 0.01 constant in train_classifier.py is used to choose a threshold, which is a different act from measuring and reporting the resulting recall at that operating point as a standalone evaluation metric — the latter has never been computed and printed/logged/written anywhere.
    • No confusion matrix has been generated.
    • No permutation feature importance has been computed.
    • No completeness-curve comparison between the classifier and the hand rule exists — completeness_by_depth() (§31.2) produces per-run numbers inside a manifest entry, which is the raw ingredient for such a curve, but no comparison figure or table against the ΔBIC+τ/σ hand rule's own completeness has been assembled.
    • The "final exam" (all 6 KIC 3542116 dips above threshold) has never been formally reported as a pass/fail result with an accompanying write-up, independent of whatever real_data_backtest() may or may not have printed to a training-run's stdout log (see §31.2's verification caveat).

    Status: C3 NOT IMPLEMENTED / NOT RUN. Do not invent accuracy, precision, recall, ROC-AUC, PR-AUC, or completeness numbers for this classifier anywhere in this specification or elsewhere. If a manifest file (models/manifest_kepler.jsonl or similar) is later found in the external data repository containing a real real_data_backtest result from an actual training run, that specific manifest entry's numbers are real, dated, sourced data and may be cited by their own manifest-provenance fields (date, training-set hash, package versions) — but as of the sources read for this document, models/ in the external exocomet-hunter-data repository contains only a .gitkeep placeholder (confirmed by direct clone and listing, 2026-09-16 — see 33_results.md). No trained model artifact and no manifest entry currently exist anywhere.

    31.4 C4 — Wire it in: BLOCKED on C3¶

    Status: NOT IMPLEMENTED, correctly blocked.

    Next Steps C4 specifies adding score.comet_probability to EventScore and to_row(), changing the flagging rule to flagged = comet_probability >= threshold (threshold chosen from C3's 1%-FPR measurement), and retaining the current physics-based ΔBIC+τ/σ rule as a reported comparison column.

    Confirmed by direct inspection of core/types.py: EventScore has no comet_probability field, and CandidateRecord.to_row() has no such column. The production flagging rule remains exactly the ΔBIC+τ/σ conjunction from research log 007 (detect/scoring.py::score_event). This is the correct state given C3 has not produced a threshold to wire in — implementing C4 before C3 exists would mean choosing an arbitrary, unmeasured threshold, which the project's own standing discipline (never invent precision the numbers don't support — see Next Steps.md PART J's explicit rejection of an invented "0-100 Priority Score" for the same reason) argues against.
