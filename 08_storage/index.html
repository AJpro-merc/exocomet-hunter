    8. Storage¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051. All three layers below are IMPLEMENTED and covered by unit tests (tests/unit/test_extract.py, tests/unit/test_ledger.py, tests/unit/test_build_local_db.py).

    The storage architecture has three layers, each with a distinct role: a permanent per-target extract (parquet), an append-only processing history (JSONL ledger), and a disposable queryable view rebuilt on demand (SQLite). None of the three is a second source of truth for another — each is described in its own module as being built from, not alongside, the layer beneath it.

    8.1 Extract format — io/extract.py¶

    Layout: <base_dir>/extract/<mission>/<sanitized target_id>.parquet, computed by extract_path(base_dir, mission, target_id). sanitize_target_id replaces spaces and path separators with underscores (e.g. "KIC 3542116" → "KIC_3542116") purely to produce a filesystem-safe name — the docstring is explicit that this is "not... reversible on its own," and that this is fine, because the original unsanitized target_id is always recovered from the file's own embedded metadata (below), never from the filename.

    File contents. time, flux, flux_err become parquet columns (pa.float64()); target_id, mission, and meta (JSON-encoded) ride along as parquet file-level schema metadata, not a sidecar file — namespaced keys exocomet.target_id, exocomet.mission, exocomet.meta_json. The module docstring gives the reasoning: keeping everything in one file means "there is only ever one thing to write atomically and only one thing that can go missing or drift out of sync," at the cost of requiring meta to be JSON-serialisable (already true of every producer in this codebase). pyarrow is used directly (not pandas.DataFrame.to_parquet) because schema metadata does not reliably survive a pandas round trip.

    Atomicity (save_extract). The table is written to a temporary file in the same directory as the final path (tempfile.mkstemp(..., dir=str(path.parent)), ensuring the later rename stays on one filesystem), then moved into place with os.replace, which is atomic on POSIX — covering both GitHub Actions runners and macOS, the two environments this pipeline runs on. A reader can therefore only ever observe the target path as either completely absent or completely written; there is no window where a half-written file is visible at the final name. If anything raises before the replace completes, the temporary file is removed in an exception handler so it can never be mistaken for a real, complete extract.

    Round-trip guarantee (load_extract). Reconstructs target_id, mission, and meta from the schema metadata and the three columns from parquet; the docstring states the result "round-trips exactly: identical arrays (float64 in, float64 out, no precision loss from parquet) and an identical meta dict for any JSON-serializable input."

    See 35_code_reference/io.md for full function signatures.

    8.2 Append-only ledger — io/ledger.py¶

    Purpose, and what it replaced. The ledger replaces an earlier pattern (results/processed_ledger.json, one JSON object rewritten whole at the end of a run) used by scripts/monitor_new_data.py. That pattern loses every completed record the instant the process is killed mid-run, because the previous good state exists only in memory until the final rewrite lands — unacceptable under a bounded (~30 minute) GitHub Actions budget where the runner can be killed at any moment. The ledger instead opens in "a" (append) mode and writes one JSON line per event, so a completed record is durable the moment append_entry returns — there is no whole-file rewrite step for a kill to interrupt.

    LedgerEntry fields (@dataclass(frozen=True)): target_id, mission (together the key), status ("success" or "failed"), timestamp_utc (ISO-8601 UTC), attempt (1-indexed, set by the caller — the ledger does not independently track attempt counts), error (message on failure, None on success), extract_path, results_path (both None when not applicable, e.g. a failure before any output existed).

    Durability mechanism (append_entry). After writing the JSON line, the function calls both handle.flush() (moves bytes out of Python's io buffer) and os.fsync(handle.fileno()) (forces them to the physical device) — the docstring is explicit that flush() alone is insufficient because the OS page cache can still hold the bytes indefinitely; fsync is what lets a record survive not just a killed Python process but a killed/rebooted runner.

    Torn-write guard, both directions. Before writing, append_entry checks whether the ledger file's last byte is a newline; if not (a previous process was killed mid-write()), it emits a leading newline first, so the new entry cannot be glued onto the end of a broken prior line, turning one bad line into two. On read, read_ledger skips (and logs) any line that fails to parse as JSON, rather than raising — so a torn trailing line from an interrupted write never causes N−1 good, already-fsync'd records to be lost.

    Derived views, all pure functions over the flat entry list: latest_entries (last entry per (target_id, mission)); get_status ("done" iff the latest entry for a key is status="success", otherwise "pending" — retryable failures and never-attempted targets are deliberately conflated here); next_targets (targets still needing processing: never-attempted first in input order, then retriable failures oldest-failure-first, excluding anything that has exhausted max_attempts or already succeeded).

    8.3 Disposable local SQLite view — scripts/build_local_db.py¶

    Explicitly not a second source of truth. The module docstring states this directly: "This script is not a second source of truth — it is a queryable view, rebuilt from scratch on demand, never committed to git, never written by CI." Every run deletes any existing --out file and rebuilds it fully from <data-repo-dir>/ledger.jsonl (and, for candidate counts, the results files the ledger points at) — a full rebuild is described as "cheap (well under a second)" given the ledger is one line per attempt across at most a few hundred targets, which the module argues avoids an entire class of incremental-sync bugs.

    Three tables (_SCHEMA in build_local_db.py): - attempts — one row per raw ledger line, the full retry history: target_id, mission, status, timestamp_utc, attempt, error, extract_path, results_path. Nothing deduplicated. - targets — one row per (target_id, mission) (primary key), the latest-status view built from latest_entries: same columns as attempts plus retries_left (computed against --max-attempts, meaningful only when status='failed'), n_candidates, n_flagged. n_candidates/n_flagged are NULL, not 0, when results_path is unset or the file doesn't exist (failed or never-attempted target — nothing to count), and 0 when the results file exists but is empty (fully processed, zero detections). The docstring calls this NULL-vs-zero distinction deliberate — it is "the whole reason this table reads the results files at all rather than trusting the ledger alone." - candidates — one row per detected event, columns mirroring CandidateRecord.to_row() (target_id, t_min, depth_ppm, duration_days, a_dur_sigma, significance, delta_bic, tau_over_sigma, signs_agree, flagged, periodic, period_days, vetting_status, vetting_reasons) plus mission, foreign-keyed to targets.

    Default output path is local.db in the current directory, deliberately not inside <data-repo-dir> — the docstring's reasoning: the data-repo directory is meant to be a git clone of the separate exocomet-hunter-data repository, and dropping a disposable, frequently-regenerated binary file inside it risks it being swept up by a stray git add -A there.

    8.4 Data integrity: what is actually checked, and what is not¶

    Mechanism Status
    Atomic file replacement (os.replace) for extracts and results files IMPLEMENTED — io/extract.save_extract, scripts/ingest.py's _write_results_jsonl
    fsync-backed durability for ledger writes IMPLEMENTED — io/ledger.append_entry
    Torn-write recovery (corrupt last line) IMPLEMENTED — both the leading-newline guard on write and the skip-and-log behaviour on read, io/ledger.py
    Round-trip fidelity of extract arrays/metadata TESTED — load_extract/save_extract round-trip, asserted in tests/unit/test_extract.py per the module's own docstring claim
    Checksums on stored data (extracts, results) NOT IMPLEMENTED. No hash/checksum of extract or results file contents is computed or stored anywhere in io/extract.py, scripts/ingest.py, or the ledger schema. A silently corrupted (but structurally valid) parquet or JSONL file would not be detected by anything in this pipeline.
    Provenance manifest (config, code version, package versions, seed, target-list hash) PLANNED, NOT IMPLEMENTED as a general mechanism — Next Steps item E3. A narrower, already-built instance exists for the classifier only: scripts/train_classifier.py's models/manifest_<mission>.jsonl records row counts, class counts, host stars, date, package versions, and training-set hash — but this is specific to classifier training data, not a general per-run provenance record for detection runs.
