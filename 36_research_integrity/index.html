    36. Research Integrity¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051. This section states the project's real, currently enforced rules — some in code, some as documented and consistently followed conventions — and separately flags what is agreed but not yet operationalized as a formal process.

    36.1 An AI never decides what counts as a comet (H1's design principle)¶

    Next Steps.md PART H, item H1 states the rule for a planned AI-review layer:

    Rule: the model never decides whether something is a comet. It receives only computed features (JSON), returns structured JSON: evidence for, evidence against, alternative explanations, recommended next test, and must be allowed to answer insufficient_evidence. Use it as a skeptic, not a cheerleader.

    Status: H1 itself is PLANNED, NOT IMPLEMENTED — no code in this repository currently sends candidate features to an external AI model for review. But the principle it encodes is already load-bearing elsewhere in the actually-built pipeline: every classification decision that exists today (the ΔBIC+τ/σ flagging rule in detect/scoring.py, research log 007) is a deterministic, documented, config-driven statistical rule — not a model output treated as ground truth. The eventual C2/C3/C4 classifier (31_machine_learning.md) is explicitly scoped as replacing a hand-set rule with a measured one, never as an opaque authority: C3's entire purpose is to produce numbers a human can inspect and decide whether to trust, and C4's design keeps the physics-based rule as "a reported fallback column so the two can be compared" rather than retiring it silently.

    PART I of Next Steps.md sharpens this further for the still-parked "AI skeptic" idea: "it may summarize, critique, propose alternative explanations, and suggest next tests; it may never alter a measurement, compute an authoritative statistic, silently change a label, or claim a discovery." This remains a design intention (PLANNED), not a built guardrail, since no such component exists yet.

    36.2 Candidate ≠ confirmation — enforced by convention throughout the project¶

    Every document in this specification, the README, and every research log consistently uses "candidate" or "candidate event" or "exocomet-like morphology" for a flagged detection, and never "confirmed" or "discovery." This is stated explicitly in the README's "Honest limitations" section: "A flagged event is a candidate, never a confirmed exocomet. Confirmation needs follow-up this pipeline cannot provide." 00_document_control.md §0.4 repeats the same distinction as a defined term. This is a documentation and naming convention enforced by consistent usage, not a runtime code check — there is no assertion anywhere in the codebase that would prevent a future contributor from writing the word "confirmed" into an output field. Its enforcement is textual and cultural, verified here by the absence of any contradicting instance found while reading the project's source and documentation for this specification.

    36.3 The blind-search protocol (D3) — PLANNED, not yet executed as a formal process¶

    Next Steps.md PART D, item D3 specifies:

    1. Tune everything only on the development set (validation stars + injections).
    2. Commit and tag the frozen configuration, e.g. v0.2-frozen.
    3. Only then run on the search targets. Record the tag in every result.
    4. Any change after looking at search results → new tag, and say so in the write-up.

    Status: PLANNED, NOT IMPLEMENTED as a formal, followed process. No git tag matching a pattern like v0.2-frozen was found referenced in any session log or research log read for this document, and no result file anywhere records "produced under tag X." The project's actual development pattern to date has been iterative — thresholds and the flagging rule itself were changed multiple times in direct response to findings against the validation targets (research logs 003 and 007 are both examples of exactly this: tune, observe a problem against KIC 3542116, fix, re-test against the same target). This is legitimate development methodology but is explicitly not the disciplined tune-freeze-run-once separation D3 describes, and the project's own tracker does not claim otherwise — D3 is correctly marked PLANNED there, not "done differently."

    36.4 What "research integrity" means concretely in this project, today¶

    Given the above, the actually-operative integrity controls in this codebase, as of this commit, are:

    • A hard-coded hold-out list (EXCLUDED_HOLD_OUT_TARGETS) that a training run cannot bypass without the code raising HoldOutError (31_machine_learning.md §31.2) — this one is a real runtime enforcement, not just a convention.
    • A validation gate (exocomet validate, scripts/run_validation.py) that exits non-zero on any missed published dip.
    • Consistent "candidate, not confirmation" language, enforced by convention/review rather than code.
    • A documented research log recording negative and inconclusive results, not only successes — research log 006 (the depth-offset investigation) is explicitly titled "partially explained, not resolved" and states plainly what it did not resolve; this document's own §31.3 follows the same discipline for the classifier.

    What is not yet in place: an external, disinterested review of any specific candidate; a formally frozen and tagged configuration used for a genuine blind run; and an operating AI-skeptic component. All three are named, agreed-upon future work (H1, D3, PART I), not silently abandoned ideas.
