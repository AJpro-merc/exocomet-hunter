    60. Security and Trust¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    60.1 Credentials in use¶

    DATA_REPO_TOKEN. A fine-grained GitHub personal access token, scoped to AJpro-merc/exocomet-hunter-data only, with Contents: Read and write permission. Stored as a GitHub Actions repository secret on AJpro-merc/exocomet-hunter (Settings → Secrets and variables → Actions) — never committed to source, never present in any file in this repository. Used identically in .github/workflows/ingest.yml and .github/workflows/train.yml:

    git clone "https://x-access-token:${{ secrets.DATA_REPO_TOKEN }}@github.com/${DATA_REPO}.git" data-repo

    GitHub's own secret-masking redacts the token value from all workflow logs automatically; this project adds no logging of its own that could bypass that. Per Session Log 2026-09-15, adding this secret was explicitly treated as the user's own action, not something an AI assistant performs on the user's behalf ("entering credentials, even a repo secret, is outside what this assistant does").

    No other credentials are handled by this project. MAST, VizieR, and the TESS Input Catalog are all queried anonymously/publicly (no API key or login required for the data accessed) — confirmed by direct reading of io/download.py and scripts/build_target_list.py, neither of which references any credential for those services. The README states this explicitly under "Data sources": "All public, no credentials required."

    60.2 GitHub Actions permissions¶

    All three workflows declare an explicit, minimal permissions: block rather than relying on the repository's default token permissions:

    Workflow permissions: block
    ingest.yml contents: write
    train.yml contents: write
    survey.yml contents: write

    contents: write is required because each workflow commits output back to a repository (either the separate data repo, via DATA_REPO_TOKEN, or — for the legacy survey.yml — this repository itself, via the default GITHUB_TOKEN). No workflow requests broader scopes (e.g. id-token, packages, pull-requests) than this. This is the full extent of the permissions review possible from static inspection of the YAML files; the actual effective permissions of the default GITHUB_TOKEN also depend on the repository's own Settings → Actions → General configuration, which is account/repo-owner-controlled state not visible from this codebase and was not independently verified from this environment.

    60.3 Concurrency and race protection as a security-adjacent property¶

    Each workflow declares concurrency: {group: <name>, cancel-in-progress: false}, ensuring a second trigger of the same workflow queues rather than running concurrently against the same data repository — this is what prevents two simultaneous pushes from racing on the same git push (a real conflict class this project has already hit once, per Session Log 2026-09-15 §11's discussion of two independent local invocations racing against the same target/path — resolved correctly by the append-only ledger design rather than by this concurrency setting, but the setting is the intended first line of defense for the automated case).

    60.4 What is explicitly out of scope / not applicable¶

    This project has no user-facing authentication, no web-exposed service, no database with access-control rules, and no handling of personal or sensitive data of any kind — its only "users" are the pipeline's own automated runs and its maintainer running CLI commands locally. There is no threat model document, and none is warranted at this project's current scope beyond the credential-handling practices described above.

    60.5 A known account-identity friction (not a security bug)¶

    Session logs document a recurring operational friction, not a vulnerability: git push from a local machine intermittently fails with Device not configured because the local keychain's active gh account (elpis-app) differs from the account that owns the repository (AJpro-merc), requiring an explicit https://AJpro-merc:<token>@github.com/... push URL as a workaround. Next Steps item 5 lists "fix git push's account mismatch properly (a persistent local credential config, not a one-off token workaround)" as still open. This is a local development-environment configuration issue, not a repository or data-security concern, and is noted here only because it involves credential/account handling.
