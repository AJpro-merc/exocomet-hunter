    1. Project Foundation¶

    Status: reflects repo state as of 2026-09-16, commit 01c2051.

    1.1 Project summary¶

    Exocomet Hunter is a Python framework (exocomet-hunter, src/exocomet/) for detecting comets orbiting other stars in NASA Kepler and TESS photometry. It is built and IMPLEMENTED for one concrete search — asymmetric, comet-like dimming events — and architected (via Detector/Vetter/Detrender/LightCurveSource abstract interfaces in core/interfaces.py) so a second kind of search can be added as a new class rather than a pipeline rewrite. Source: README.md, pyproject.toml description field ("A framework for detecting asymmetric, comet-like transit events in Kepler and TESS light curves").

    1.2 The scientific problem¶

    A planet is a solid, opaque disc: it covers and uncovers its star at the same rate, producing a transit that is symmetric in time and strictly periodic. A comet instead drags a tail of dust (and, closer to the star, gas) behind its nucleus. Two physical consequences follow:

    1. The transit is asymmetric — the compact, relatively opaque head blocks light quickly (steep ingress), while the more diffuse, extended tail clears more slowly (long egress).
    2. The transit is not periodic on any observable timescale — exocomets are inferred to be on long, eccentric orbits, so events recur irregularly if at all, with varying depths.

    That asymmetry is the entire detection signal this project exploits. Section 4 (04_exocomet_physics.md) gives the physical picture in more detail and grounds it in the parametric model actually implemented in code; section 5 (05_detection_theory.md) gives the mathematics and the discriminating statistics.

    1.3 The computational problem¶

    Kepler alone measured ~200,000 stars' brightness every 29.4 minutes for four years; TESS covers most of the sky at multiple cadences (20 s–1800 s) across overlapping sectors. Two problems compound:

    • Scale. A full-sky search means searching hundreds of thousands of stars, each with tens of thousands of photometric points, for an event that individually looks like little more than a modest, temporary dimming.
    • Rarity and ambiguity. Genuine exocomet-like dips are rare, and the same asymmetric-dip shape can be produced by things that are not comets: stellar flares (opposite sign), eclipsing binaries (periodic), starspot rotation, and instrumental artefacts (thruster firings, thermal settling, sector/quarter boundaries). Distinguishing a real candidate from these is most of the engineering and statistical effort in this project (see docs/research_log/ for concrete, resolved instances of this problem).

    Measured performance addressing the scale problem (README, §"Does it work?"): full-mission processing of one Kepler star (65,000 cadences, four years) takes 0.8 s. Source: README.md; per the Findings Log (2026-09-13), this was measured, not estimated, on the author's own machine (Apple M4, 10 cores). UNVERIFIED against an independent environment or a later code version — no CI benchmark currently reproduces this number (see 35_code_reference gaps and Next Steps item E7, "Benchmarks — not yet built").

    1.4 Proposed solution¶

    An asymmetric-dip detection framework: detrend a light curve, flag statistically significant local dimmings, fit two competing parametric shapes (a symmetric Gaussian and a Gaussian-ingress/exponential-egress "comet" profile) to each one, and rank/flag by a combination of Bayesian model comparison (ΔBIC) and the fitted tail-to-core ratio τ/σ. This is IMPLEMENTED as AsymmetricDipDetector (detect/comet_detector.py), the first and — as of this commit — only concrete subclass of the Detector ABC (core/interfaces.py). See section 5 for the full mechanism and section 9 for the architecture that makes it a "first implementation" rather than the only possible one.

    1.5 Core research question¶

    Stated in the project's own terms (README, Findings Log): can an independent-method, statistically characterised search recover known exocomet transit signatures in Kepler data, and can its own detection sensitivity be measured well enough to say what it would have missed? This is explicitly not framed as a discovery hunt — see 1.7 below.

    1.6 Objectives¶

    Primary (scientific/technical): - Recover previously published exocomet transit epochs in Kepler data as a validation gate, before trusting any result from a blind search. IMPLEMENTED and TESTED: AsymmetricDipDetector recovers all six dips reported by Rappaport et al. (2018) for KIC 3542116, within 0.184 d of the published epoch in the worst case (README; cross-checked in docs/research_log/003 and 006). Automated via scripts/run_validation.py / exocomet validate (Next Steps B6, done 2026-09-15). - Quantify detection sensitivity via injection-recovery, not just report a raw detection count. PARTIAL: calibration/injection.py exists and the README quotes a 50% floor near 750 ppm and 100% recovery above 1000 ppm from 200 synthetic injections — but Next Steps item B8 flags these specific numbers as stale, measured before the A1 (cadence-in-days) and A4 (ΔBIC+τ/σ flagging rule) fixes landed, and not yet re-measured. Treat the README's injection numbers as UNVERIFIED against the current code version until B8 is closed.

    Secondary (methodological): - Rank candidates by a shape statistic that is actually diagnostic of comet-like asymmetry rather than one that merely detects "not symmetric." Resolved via research log 007 — see 05_detection_theory.md. - Build toward a trained classifier (Next Steps PART C) to eventually replace the hand-set ΔBIC/τ/σ flagging rule. PLANNED/PARTIAL: scripts/generate_training_labels.py and scripts/train_classifier.py exist; per Next Steps, the classifier's live-data backtest step is not fully verified (hung during testing, root cause the same class of MAST timeout issue documented elsewhere in this project).

    Engineering: - Stream-and-discard photometry rather than mirroring the archive locally (§1.7, §7, §8). - A resumable, crash-safe ingestion pipeline able to run inside a bounded GitHub Actions budget and be killed at any point without losing completed work. IMPLEMENTED: scripts/ingest.py, io/ledger.py. Per Next Steps, "proven end-to-end on GitHub's own infrastructure... every step succeeds except the final push, which needs DATA_REPO_TOKEN" — i.e. BLOCKED on a credential the automated pipeline does not yet have, as of the date in this document's Status line.

    Scientific extensions (not yet built): cross-mission validation, a physically-motivated comet light-curve simulator, a second independent detector, debris-disc vs. control population comparison. All PLANNED — see Next Steps PART F.

    1.7 Scope and non-scope¶

    In scope / actually implemented: - Single-star, single-method asymmetric-dip detection on Kepler and TESS light curves fetched from MAST. - Statistical characterisation of that one method's sensitivity via synthetic injection. - A resumable batch-ingestion pipeline with an append-only ledger and a disposable local SQLite query view.

    Explicitly out of scope, and why (README, "Honest limitations"; Next Steps): - No pixel-level vetting. vetting/__init__.py is currently an empty module (module docstring only: "Catalogue cross-matching and false-positive checks."). NOT IMPLEMENTED. A background eclipsing binary bleeding into the photometric aperture cannot currently be excluded. Flagged as the single biggest missing capability by two independent external reviews recorded in the project's own Next Steps (item J1). - No confirmed discoveries. This project's vocabulary intentionally stops at "candidate" (§0.4). Confirmation requires follow-up (e.g. pixel-level analysis, independent-instrument corroboration) this pipeline does not provide. - No trials-factor correction. Per-event significance is not corrected for the number of places searched; the look-elsewhere effect applies to any blind search using this tool. PLANNED (Next Steps D5, J2 — an empirical look-elsewhere measurement via time-reversed/null light curves). - Not positioned as a discovery hunt. Kepler has already been searched, including a 2025 neural-network search of all 201,820 stars (README). This project positions itself as an independent-method cross-check with characterised sensitivity, explicitly not a claim to find something a prior search missed. - SIMBAD/Gaia cross-matching — mentioned as a data source in the README's "Data sources" section, but NOT IMPLEMENTED in code as of this commit (vetting/__init__.py is empty; no SIMBAD/Gaia query exists anywhere in src/exocomet/). See 06_data_sources.md.

    1.8 Expected outputs¶

    • Per-target candidate tables (CandidateRecord.to_row(), core/types.py) — one row per detected dimming event with its geometry, asymmetry, model-comparison, and (if run) vetting outcome.
    • An append-only processing ledger (io/ledger.py) and a disposable SQLite view over it (scripts/build_local_db.py) for ad-hoc querying of what has been processed and what was found.
    • Research-log write-ups (docs/research_log/) documenting real findings, including negative or partial results (e.g. the depth-offset investigation, 006, explicitly closes with "not resolved").
    • A planned but not-yet-built trained classifier, dashboard, and case-file export (Next Steps PART C, H2, J9) — all PLANNED, none IMPLEMENTED as of this commit.

    1.9 Project philosophy¶

    Atharva Joshi's own stated preference, recorded in the project's Next Steps document (item H5): build-first. The project has been built and iterated aggressively — with a documented practice of testing claims against real data and reversing course when a hypothesis fails (e.g. three separate falsified hypotheses in research log 003; three tested and only partially confirmatory hypotheses in research log 006) — with a deferred, still-owed "learning pass": a plain-language walkthrough of every module so the author can explain every design choice himself, independent of who or what wrote the code originally. That learning pass is itself listed as PLANNED, not done, in Next Steps as of this document's date.
